# Локальный стенд и проверки

Полноценного тест-фреймворка в проекте нет. Здесь — сценарные проверки на
голом bun против **живого** Postgres и поднятого приложения. Они появились
потому, что три самых дорогих бага (угон аккаунта, потеря оплаты, двойное
начисление) на типах и линтере не ловятся в принципе: нужны настоящая база
с её уникальными индексами и настоящий HTTP.

Боевого Telegram-токена не требуется и не должно быть: `TELEGRAM_DISABLE_BOT=true`
не даёт Telegraf забирать апдейты — иначе стенд увёл бы их у продового бота.

## Запуск

```bash
cd apps/nexer-back

# 1. база
docker compose -f test/docker-compose.yaml up -d
export DATABASE_URL="postgresql://postgres:test@localhost:54329/nexer_test?schema=public"
bunx prisma migrate deploy

# 2. проверки, которым приложение не нужно
bun run test/concurrency.test.ts     # гонки: бонусы, триал, идемпотентность
bun run test/auth.test.ts            # подписи initData и вебхука

# 3. проверки по HTTP — нужен стенд
bun run test/mock-remnawave.ts &     # заглушка панели на :59999
bun run build
ENV_FILE=test/.env.stand node dist/main.js &   # PowerShell: $env:ENV_FILE=...

bun run test/e2e.test.ts             # авторизация, защищённые ручки, вебхук
bun run test/webhook-retry.test.ts   # оплата при упавшей панели + ретрай
```

> Боевой `.env` трогать не нужно: `ENV_FILE` подставляет стендовый конфиг.
> Без этой переменной приложение читает `.env`, как и раньше.

## Что именно проверяется

**`auth.test.ts`** — криптография без приложения.
initData с подменённым `id`, самодельная строка без подписи, подпись чужим
токеном бота — всё должно отвергаться. Плюс демонстрация, зачем вебхуку нужно
сырое тело: пересобранный `JSON.stringify` даёт другой HMAC.

**`concurrency.test.ts`** — гонки на реальной базе.
Прогоняет старую и новую логику рядом: на 4 параллельных клеймах старая
выдавала **20 дней вместо 5**, новая — ровно 5. То же для триала и для
повторной доставки вебхука.

**`e2e.test.ts`** — по HTTP.
Главное здесь — попытка авторизоваться под чужим telegram id тем способом,
который работал до починки `telegram.strategy.ts`.

**`webhook-retry.test.ts`** — самый важный сценарий.
Панель недоступна в момент оплаты → событие остаётся `failed`, а не
«обработано»; ретрай Tribute доводит подписку до выдачи; платёж не двоится.

Именно этот сценарий поймал ошибку в первой версии идемпотентности: событие
помечалось обработанным **до** работы, и сорвавшаяся выдача превращалась в
тихую потерю оплаты — клиент заплатил, VPN не получил, а ретрай провайдера
отбрасывался как дубликат. Отсюда статусы `processing/completed/failed`
в `webhook_event`.

## Чего здесь нет

Юнит-тестов на сервисы, моков Prisma, покрытия. Это сценарные проверки на
критичных путях, а не замена тест-фреймворку. Если будете заводить полноценный
`jest`/`vitest` — эти сценарии стоит перенести туда как есть, они описывают
реальные инциденты.
